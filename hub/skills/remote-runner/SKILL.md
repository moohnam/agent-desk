# 원격 러너 설치와 연결

사용자가 지정한 머신에 `runner:shared`를 준비하고, 지정한 허브에서 그 작업공간을 볼 수 있게 합니다. 현재 공유 러너는 원격 머신에 작업·대화 원본과 실행 엔진을 함께 둡니다. 접속 가능한 허브가 여러 개여도 같은 작업을 봅니다.

## 먼저 확인할 것

- SSH 대상, 접속할 허브와 실행 계정을 기존 맥락·등록된 연결에서 확인합니다. 확정할 수 없는 항목만 묻습니다. SSH 별칭을 실제 호스트명으로 임의 변경하지 않습니다.
- 허브의 `GET /api/workspaces`와 필요한 연결의 `/state`를 조회하고, 원격에서 기존 서비스·설치 경로·러너 포트·데이터 디렉터리를 확인합니다. 정상 러너가 이미 있다면 재설치보다 기존 연결을 재사용합니다. 목록에 노출되지 않는 인증 파일을 통째로 출력하지 않습니다.
- 대상 저장소의 `package.json`, `hub/src/config.ts`, `hub/src/runner/shared.ts`, `README.md`의 공유 러너 절차를 읽습니다. 아래 명령은 현재 구현의 형태이며, 실행할 버전의 코드와 다르면 그 버전을 기준으로 확인합니다. 설치할 소스는 확인한 저장소와 버전으로 고정합니다.
- `ssh -o BatchMode=yes -o ConnectTimeout=10 <대상>`으로 접속을 확인하고 OS·아키텍처·Node 버전·사용할 CLI의 설치와 인증 상태를 확인합니다. 인증 실패나 호스트 키 불일치가 나면 우회 옵션으로 재시도하지 말고 해당 원인을 보고합니다. 새 호스트 키는 신뢰할 수 있는 지문으로 확인합니다.
- Node 버전은 설치 버전의 `engines`에 맞춥니다. 필요한 의존성은 사용자 권한으로 설치합니다. CLI 로그인은 그 머신의 실행 계정을 그대로 쓰며, 홈 디렉터리나 다른 머신의 인증 파일을 덮어쓰지 않습니다. 지원 엔진 목록은 실제 로그인 성공을 보장하지 않습니다.

## 설치·상시 실행

1. 기존 러너의 고정 주소, 데이터 디렉터리, 작업공간 ID를 기록합니다. 같은 데이터 디렉터리에 실행 프로세스를 둘 띄우지 않습니다. 기존 `runner:remote` 작업을 공유 러너로 이전하는 것은 별도 이관 작업이며, 새 DB로 바꿔 기존 대화가 이전됐다고 보고하지 않습니다.
2. 새 설치는 사용자 디렉터리에 버전별 코드와 영속 데이터를 분리합니다. 예를 들어 코드 릴리스와 `~/.local/share/agent-desk/shared`를 따로 둡니다. 기존 체크아웃에 수정이 있으면 덮어쓰거나 강제로 되돌리지 않습니다. 잠금 파일에 맞춰 의존성을 설치하고 해당 엔진의 모듈 로딩을 확인합니다.
3. 실행 계정·PATH·Node 절대 경로와 다음 환경을 지정합니다. 포트는 미사용 여부를 먼저 확인해 고르며, 예시 번호가 비어 있다고 가정하지 않습니다.

   ```sh
   export AGENT_DESK_SHARED_DIR='<원격의_데이터_절대경로>'
   export AGENT_DESK_SHARED_ADDRESS='<사용자@서버>'
   export AGENT_DESK_SHARED_PORT='<원격_러너_포트>'
   ```

   위 환경에서 저장소 루트 기준 `node hub/src/runner/shared.ts` 또는 `npm run runner:shared`를 실행합니다. 공유 러너는 `127.0.0.1`에만 바인딩합니다. 프로젝트 작업 경로는 원격 머신 기준이며, 러너 설치 요청만으로 테스트 프로젝트나 에이전트 작업을 만들지 않습니다.
4. Linux에서는 가능한 경우 `systemd --user` 서비스로 관리합니다. 작업 디렉터리, Node 절대 경로, 위 환경과 재시작 정책을 명시하고 비밀값을 unit이나 명령 인수에 넣지 않습니다. 로그아웃 뒤 유지 여부도 확인합니다. linger 변경에 권한이 필요하면 그 조건을 설명합니다. 사용자 서비스가 불가능하면 지원되는 대안을 선택하되 tmux/nohup은 부팅 후 자동 복구를 보장하지 않는다고 알립니다. 다른 OS는 해당 사용자 서비스 관리자를 사용합니다.
5. 기존 서비스 교체가 필요하면 실행·대기·백그라운드 작업, 승인·질문, 미전달 입력을 확인합니다. 사용자가 실행 중 작업의 중단까지 승인하지 않았다면 유휴 시 교체하고, 교체 직전에 같은 항목이 비어 있는지 다시 확인합니다. 기존 릴리스와 서비스 설정으로 복구할 수 있게 준비하고, 기동 실패 시 반복 재시작 대신 원인을 확인합니다. 네트워크 단절과 러너 프로세스 종료는 다릅니다.

## 허브 연결

1. 허브 머신에서 원격 러너의 loopback 포트로 SSH 터널을 만듭니다. 기존 정상 터널은 재사용하고, 새 터널은 전용 프로세스로 관리합니다.

   ```sh
   ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes \
     -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
     -L 127.0.0.1:<허브측_빈포트>:127.0.0.1:<러너_포트> <SSH대상>
   ```

   값은 검증해 인수 배열 또는 올바른 셸 인용으로 전달합니다. 호스트 키 검증을 끄거나 포트를 외부에 공개하지 않습니다. 서버와 허브가 다른 머신이면 터널은 에이전트가 일하는 머신이 아니라 **허브 머신**에 있어야 합니다. 터널도 로그아웃·재부팅 후 유지되는지 선택한 서비스 방식으로 확인합니다.
2. 기존 허브 연결이 정상이라면 발급 당시 토큰 파일이 없어도 연결을 재사용합니다. 새 연결 키가 필요할 때만 **서비스와 같은 `AGENT_DESK_SHARED_DIR`**에서 다음 명령을 실행합니다. 다른 허브의 키를 재사용하지 않습니다.

   ```sh
   npm run runner:shared -- grant <허브이름> <새_토큰파일_절대경로>
   ```

   이 명령은 0600 파일을 만들고 peer ID·작업공간 ID·파일 위치만 출력합니다. 생성한 peer ID를 보관합니다. 토큰을 터미널·채팅·로그·프로세스 인수에 출력하지 않습니다. 보호된 SSH 전송으로 허브 머신의 접근 제한 임시 파일에 옮깁니다.
3. 허브 머신에서 토큰 파일을 메모리로 읽는 HTTP 클라이언트로 `POST /api/workspaces`에 `{name, url, token}`을 전송합니다. `url`은 예를 들어 `http://127.0.0.1:<허브측_포트>/`입니다. 허브가 다른 머신이면 그 머신에 SSH 접속해 로컬 HTTP 클라이언트를 실행할 수 있는지 먼저 확인합니다. 원격 등록에는 허브 머신의 관리 권한이 필요하며, 전체 허브 포트를 다른 머신으로 전달해 관리 권한 검사를 우회하지 않습니다. 출력은 토큰이 없는 응답의 ID·연결 상태로 제한합니다. 기존 연결 키를 교체하는 요청이면 확인한 연결 ID의 `PUT /api/workspaces/{id}`를 사용합니다.
4. 등록 실패 시 먼저 신원·터널·기존 연결을 조회합니다. 같은 작업공간을 중복 등록하거나 새 키를 무한히 발급하지 않습니다. 이번 시도에서 새로 발급한 미사용 peer만 필요에 따라 `revoke <peer-id>`로 정리합니다. 기존에 쓰던 peer를 폐기하지 않습니다. 이번 키의 발급 원본과 허브 전달 사본은 임시 파일로 만들고, 등록 성공 또는 실패 정리가 끝나면 둘 다 지웁니다. 기존 인증 파일이나 사용자가 별도 보관을 요청한 파일은 이 정리 대상이 아닙니다.

## 검증과 완료 보고

- 서비스 상태와 실제 리스닝 주소, 터널 상태, `/v1/identity`의 작업공간 ID, 허브 연결 목록과 `/api/workspaces/{id}/state`를 대조합니다. 인증 요청은 토큰을 메모리로만 읽습니다. 연결 이름이나 포트 응답만으로 같은 작업공간이라고 판단하지 않습니다.
- 기존 연결이면 프로젝트·작업·세션의 보존을 확인합니다. 새 설치면 연결과 엔진 가용성까지 확인합니다. 실제 에이전트 분석은 사용자가 테스트 작업을 요청했을 때만 만들며, 메시지 접수·러너 수신·실행 완료를 구분합니다.
- 서비스와 터널을 끊는 장애 검증은 기존 작업에 영향을 줄 수 있습니다. 필요한 경우 격리 환경에서 하거나 사용자 요청 범위에 맞는 유휴 시점에 수행합니다.
- 머신·계정, 설치 버전, 서비스 이름, 데이터 경로, 허브 연결 ID·작업공간 ID, 검증한 엔진, 실제 확인 결과와 남은 조건을 보고합니다. 비밀값은 보고하지 않습니다. 연결을 못 마쳤다면 실패 지점과 남은 작업을 명확히 적습니다.

## 현재 신뢰 경계

- 현재 허브 연결 키는 해당 작업공간 전체를 조작하는 권한이며, 읽기 전용·프로젝트별 권한·자동 만료를 제공하지 않습니다. SSH 암호화만으로 사용자의 권한이 분리되지는 않습니다.
- 다중 사용자 머신에서는 loopback 접속 자체가 동일 OS 사용자 인증이 아닙니다. 현재 허브는 loopback을 로컬 관리자로 신뢰하므로, 신뢰하지 않는 계정과 함께 운영하려면 계정·서비스 격리 또는 추가 인증이 먼저 필요합니다. 다른 사용자의 SSH·방화벽·서비스 설정을 임의 변경하지 않습니다.
- 이 스킬이 접속 키를 새로 발급했다고 기존 구현의 권한 분리·폐기 경합까지 해결된 것으로 설명하지 않습니다. 더 강한 격리가 필요한 배포는 충족하지 못한 조건을 보고하고 그 설계에 의존하는 배포를 멈춥니다.
